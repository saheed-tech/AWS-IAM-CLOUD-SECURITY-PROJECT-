In this hands-on cloud security project, I worked with AWS Identity and Access Management (IAM) to control how users interact with specific Amazon EC2 instances. My goal was to apply the principle of least privilege—ensuring users can only perform the exact actions they need, and nothing more. To achieve this, I tagged three EC2 instances (IT, Human Resource Management, and Advert) and used those tags inside a custom IAM policy to control who could start or stop them.

I created an IAM policy that blocked start/stop actions on the sensitive IT/HRM instance, while still allowing start/stop on non-sensitive instances like the Advert server. This policy was attached to a Developers IAM group, and individual users were added to the group so access could be managed cleanly at scale. I also configured an AWS account alias to make the login URL easier and more professional for team members accessing the AWS Management Console or using the AWS CLI.

Finally, I tested the setup by logging in as an IAM user and attempting to start and stop each instance. The results matched the design: actions on protected instances were denied with an “Access denied” message, while approved instances responded successfully. This exercise strengthened my understanding of tag-based access control, IAM policy design, and practical cloud security validation—key skills for any cybersecurity analyst working in modern cloud environments.
